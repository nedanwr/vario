# Architecture notes

This document records the design decisions that are not obvious from the code.

## Pipeline

```
source adapter (reads the source database read-only)
    │  normalize, apply collection mode, redact secrets
    ▼
spool (local SQLite): destinations · queue · cursors · fingerprints · lease
    │  deliver to the selected destination only: batched, gzip JSONEachRow
    │  over HTTP(S), retried with backoff; operational user, no DDL
    ▼
ClickHouse   (schema, users and grants: `vario init` / `vario migrate`, admin)
```

`vario run` (foreground or under launchd) and `vario backfill` use the same `collector` package. One goroutine per source synchronizes into the spool; one delivery goroutine drains the spool.

## T3 Code: snapshot boundary and change detection

- T3 Code is event-sourced. Projection tables (`orchestration_v2_projection_*`) hold current state; `orchestration_events` is the event log.
- `orchestration_v2_projection_metadata` row `thread-projections` holds the projector's high-water sequence `P`. Every read happens inside one SQLite read transaction (a WAL snapshot) and is bounded by `P`, so a snapshot of the projections and the event cursor agree exactly. Events after `P` are left for a later poll.
- Events are used only as **change notifications**. Several event types carry partial payloads (for example, `provider-turn.updated` events contain either `tokenUsage` or `turnTokenUsage`, never both), so the touched entities are re-read from the projections inside the same transaction.
- Sequences may have gaps (compaction). The cursor is "last processed sequence", queried with `sequence > cursor`, so gaps are harmless. If the `event-log-prune-mark` is beyond the cursor the collector reconciles by re-reading all projections. A periodic reconciliation (default 6 h) also covers missed events and schema drift.
- The cursor also stores the `event_id` at its sequence (`anchor`). Event ids are unique and immutable, so a different id at that sequence means the database was replaced or restored, even when the new log is longer than the old one. A log whose maximum sequence is below the cursor is treated the same way. Both start a new epoch (see versions) and a full re-read. A missing anchor event (pruned) is not treated as a replacement.
- The source database is opened with `mode=ro` and `query_only`. Vario never writes, migrates, checkpoints or vacuums it. The runtime schema is inspected (cached by `PRAGMA schema_version`) and optional columns are only selected when present.

## Durability and idempotency

- Records and the cursor that produced them are committed in **one spool transaction**. The cursor never advances past data that is not durably queued. A snapshot only writes its cursor after every batch is committed; an interrupted snapshot is simply repeated.
- **Fingerprints** (hash of the normalized row without its version, plus the privacy policy fingerprint) suppress re-sending unchanged records. This keeps reconciliation and noisy events (for example `thread.visited`) cheap. Changing the privacy settings changes the fingerprint and re-emits rows.
- The spool is bounded (`spool.max_size_mb`). When full, collection pauses without advancing cursors.
- Delivery is at-least-once: entries are deleted from the spool only after ClickHouse acknowledges the insert, so a lost acknowledgement causes a resend, possibly grouped differently. Delivery uses `insert_deduplication_token` (tables set `non_replicated_deduplication_window = 1000`), so a retried identical batch is usually dropped by ClickHouse, but only within that window. Correctness does not depend on this: see versions.
- One collector per data directory holds a lease in the spool (TTL 30 s, renewed every 10 s). The lease records host and PID; a lease whose process no longer exists on this host is taken over immediately. If renewal finds the lease taken by another process, the collector cancels itself so two collectors never keep running.

## Versions and deduplication in ClickHouse

- Mutable tables use `ReplacingMergeTree(version)`. `version` is `epoch << 44 | P`: the projector sequence at read time, with an epoch that increments if the source database is replaced or its event log restarts, so newer states always win. Re-reading unchanged state yields the same version, so re-sent rows are identical.
- Merges are asynchronous. Query through the `*_latest` views (`FINAL`, which also deduplicates across partitions) or `argMax(..., version)`. The provided `token_usage_daily` and `tool_usage` views already do this, so updated or retried provider turns are counted once. This is covered by integration tests against ClickHouse 24.8 and 25.8, including ambiguous (committed but unacknowledged) inserts.
- Partition keys use only immutable values. Conversation-scoped tables are partitioned by `toYYYYMM(conversation_created_at)` so all versions of a row share a partition and replace each other. Rows whose conversation is missing from the source fall back to 1970-01.
- `raw_events` is keyed by `(source_id, sequence, event_id)`. Events are re-sent with a newer version when a snapshot is repeated; `raw_events_latest` collapses them.

## Token usage semantics (validated against real T3 Code data)

- `turnTokenUsage` is the provider-reported consumption of a turn. In every observed record `inputTokens >= cachedInputTokens + cacheCreationTokens` and `outputTokens >= reasoningTokens`: cache and reasoning counts are subsets. Vario stores them as reported and never adds them together. It derives `uncached_input_tokens` only when input, cached and cache-creation are all reported and consistent.
- `tokenUsage` is a context-window snapshot (`usedTokens = inputTokens + outputTokens` in every observed record). It is stored in `context_*` columns and must not be summed as consumption.
- Missing or `unavailable` usage is stored as NULL with `usage_status`, never as zero. `partial` usage carries the counts T3 Code reported; they are stored as reported (a lower bound) and the view counts such turns in `turns_incomplete_usage`. The raw usage objects are kept in `attributes` for provenance.
- `usageScope` is stored in `usage_scope` and `token_usage_daily` groups by it. Only `main_agent` (with `hasSubagents = false`) has been observed. If T3 Code starts reporting subagent or cumulative scopes, summing across scopes could double count; that aggregation policy is deliberately left to the query.
- `model` comes from `turnTokenUsage.models` when reported (`model_source = 'usage'`), otherwise from the run's model selection (`'run'`).

## Messages vs. turn items

User and assistant messages appear both in the messages projection and as `user_message` / `assistant_message` turn items. Text is stored once, in `messages`. The corresponding `execution_events` rows carry `message_id` and no text, so they can be used for ordering without double-counting.

## Privacy enforcement point

Privacy filtering and redaction run during normalization, before records reach the spool, so the local spool never holds more than the configured mode allows. Non-`full` modes keep only an allow-list of keys in `attributes` and in raw event `metadata`; unknown fields are only kept in `full` mode. Kept attributes and metadata are redacted in every mode. Project titles and workspace paths count as content (messages mode and above).

Redaction is a set of regular expressions for known credential formats and credential-named assignments. Each rule declares literal hints (for example `sk-ant-`, `authorization`, `token`); a rule is only evaluated on the lines that contain one of its hints and the following line. Every match of a hinted rule contains a hint on its first line, so results equal a full scan (verified by a test against a naive implementation), at several times the throughput.

## Configuration

- One resolution function (`config.Resolve`) is used by every command, the collector, backfill and the background service: `--config`, `$VARIO_CONFIG`, `$VARIO_HOME/config.toml`, `~/.vario/config.toml`. `service install` embeds the resolved absolute path in the LaunchAgent, so the service keeps reading the same file; configuration changes need only `service restart`.
- The default data directory is `$VARIO_HOME/data` or `~/.vario/data`. `init` writes it as an absolute path, because the LaunchAgent runs with `--config` but without the shell's `$VARIO_HOME`: an empty `data_dir` would resolve to `~/.vario/data` there and split the spool, cursors and lease between CLI and service. `Config.DataDirImplicit` records an empty value; `service install` refuses such a file when the service would resolve a different directory, and `doctor` reports it. A test runs the CLI in a separate process without `$VARIO_HOME`, as the service does, and compares the state it sees.
- Writes never regenerate an existing file. `config.Update` edits only the lines of the changed keys and verifies the result by decoding: the new document must equal the old one plus exactly the requested values, otherwise the edit is refused and the user is pointed to `vario config edit`. A line counts as a key or table header only if the text before it is a complete TOML document, which keeps look-alike lines inside multi-line strings and arrays from being edited. The result must parse (unknown keys are rejected) and validate before it is written.
- Writes go to a `0600` temporary file in the same directory, are fsynced and renamed over the original, and the directory is synced; a failure leaves the original intact. A `config.toml.lock` file (O_EXCL, considered stale after 30 s) serializes writers across processes, and callers that read the file earlier (interactive `init`, `config set`, `config edit`) pass its SHA-256 fingerprint so a concurrent change is detected instead of overwritten.
- `init` keeps all answers in memory and writes the configuration once, after the summary is confirmed. ClickHouse provisioning happens earlier, only after its own confirmation of the displayed plan, and an interruption afterwards says which changes remain. The one exception to "nothing local before saving" is the password of a user guided setup is about to create (see below).
- **Pending credentials**: before a plan containing `CREATE USER` is applied, the new user's endpoint, database, name and password are written to `pending-credentials.json` next to the configuration (`0600`, atomic). If that write fails, nothing is applied. After `Apply`, the entry is dropped only if the user certainly does not exist: the step was not attempted and no earlier run recorded it, or it failed and `system.users` does not list it. After the configuration is saved, the entry for the saved endpoint and user is dropped once the password file holds the same password. The file holds a list, so a second created user never overwrites an unresolved one. An unreadable file is reported and never overwritten, and creating users is then refused. The next `init` offers to resume (prefill and verify, falling back to guided setup, which offers the kept password for that user name), keep or delete (confirmed) each entry. Entries whose password the saved configuration already uses are cleaned up. This covers SIGKILL and crashes because the file exists before the user does; nothing relies on a handler running.
- **Interrupts**: interactive `init` traps SIGINT/SIGTERM for its whole run. The handler restores the terminal state if a hidden prompt disabled echo, prints a notice prepared in advance under the prompter's mutex (the interrupt arrives on another goroutine while the wizard blocks on input), and exits with 130. Other commands that read a hidden password install the same handler only around the prompt. Re-running it diffs the reviewed configuration against the loaded one (`config.Diff`) and applies only the changed keys. The operational password stays in the separate password file; no password is accepted as an argument.

## ClickHouse access: administrative and operational

- Two kinds of credentials. The **operational** user (`clickhouse.username` plus the password file) is the only one the collector, backfill and the background service use. **Administrative** credentials are asked for by guided `vario init` and `vario migrate`, held in memory for that command, and never written anywhere.
- The separation is enforced by types. `clickhouse.Client` (operational) only inspects (`InspectSchema`, `CheckDestination`, `CheckConnection`) and inserts. Everything that changes the server (`Apply` of a plan: databases, users, grants, schema) is a method of `clickhouse.Admin`. The collector's `Sink` interface is `CheckDestination` plus `Insert`; a test runs the collector against a recording server and asserts that no statement other than inspection was issued.
- Changes are **plans**: ordered `Step`s with a kind (database, user, privileges, schema), a summary and display SQL. Secrets never appear in display SQL; steps that carry one (`CREATE USER` with a hash) keep it in a separate field, and it is redacted from error messages. `Apply` runs steps in order, stops at the first failure and reports applied, failed and not attempted steps, because ClickHouse DDL is not transactional. Every step is idempotent or re-planned from inspection, so applying again resumes.
- New users are created with `IDENTIFIED WITH sha256_hash BY '<hex>' SALT '<hex>'`, with the salted hash computed locally (SHA-256 of password followed by salt; verified against 24.8.14.39 and 25.8.33.6, including login with the generated password). Plain `CREATE USER` (no `IF NOT EXISTS`) fails for an existing user, so an existing account is never modified by accident. Existing users only ever receive `GRANT`s, after explicit confirmation.
- Operational grants are scoped to objects: `SELECT, INSERT` on each of the eight tables, `SELECT` on each view and on `vario_meta`; one `GRANT` per object, no `*.*`, no `GRANT OPTION`. `SELECT` on the tables also lets views run under the default `SQL SECURITY INVOKER`; ClickHouse lists an object in `system.tables` only to users with a privilege on it, which the schema check relies on.
- Grant **assessment** (admin side) reads `system.role_grants` (transitively, tracking whether each role is reachable through default roles) and `system.grants`. A requirement is covered by a matching access type (`ALL` included; ClickHouse expands `GRANT ALL ON db.*` into individual types) on `*.*`, `db.*` or `db.table`. Partial revokes, column-level grants and non-default roles make the result *inconclusive*, not insufficient. Settings profiles, quotas and host restrictions are not evaluated. The assessment is advisory.
- The operational login check (`CheckConnection`) runs as the operational user and reports each finding as confirmed, failed (`Issues`) or not verified (`Unverified`). `Ready` means nothing failed, and `Verified` means nothing failed and nothing was inconclusive. It reads the schema and `vario_meta` (everything the collector reads) and `getSetting('readonly')`. It runs `CHECK GRANT` for INSERT on each table and SELECT on `vario_meta`. That is explanatory only, and absent on 24.8, where it is a syntax error. Last, it sends an `INSERT ... FORMAT JSONEachRow` with an empty body to every table, built by the same `insertParams` as a delivery (same settings and a deduplication token). ClickHouse authenticates, applies the settings profile and constraints, checks privileges, `readonly` and already exhausted quotas before reading data, so the probe writes nothing. Verified against 24.8 and 25.8 with real users: missing grants (497), a `readonly = 1` profile, a `CONST` constraint on `input_format_skip_unknown_fields` (452), and `MAX query_inserts = 1` (201). Codes 164, 201 and 452 are classified as a *session restriction*, not a missing privilege. On 24.8, a `readonly = 1` session refuses even the output-format setting of Vario's queries (164, "in readonly mode"). The check maps that to a read-only issue instead of an authentication failure. Data-dependent limits (written-bytes quotas, disk space, memory) are not exercised; no test rows are written and no probe table exists.
- Users whose `system.users.storage` is not `local_directory`, `replicated` or `memory` (for example `users_xml`, `ldap`) are treated as not modifiable with SQL.

## ClickHouse schema and migrations

- `SchemaVersion = 2`. Version 1 is the Vario 0.1 schema (eight tables, ten views, no recorded version). Version 2 adds `vario_meta` (`MergeTree`, append-only, tagged with `COMMENT 'vario:meta'`) holding `destination_id` (a random UUID) and `schema_version`. Readers take the *first* destination id and the *highest* version, so repeated or concurrent migrations cannot change the identity.
- `InspectSchema` reads `system.databases`, `system.tables`, `system.columns` and `vario_meta`. Existing objects with Vario's names must match: tables need a `ReplacingMergeTree`-family engine whose only non-literal argument is `version` (from `engine_full`; the path and replica literals of replicated and shared engines are ignored), the expected sorting key (`sorting_key` against the DDL's `ORDER BY`) and every expected column with the expected type (parsed from the DDL); extra columns are allowed. `vario_meta` must carry Vario's tag. A view is Vario's when it carries a `vario:` tag, or has no comment and its `as_select` equals (ignoring whitespace and identifier quoting) one of the exact queries Vario 0.1 created it with (`viewDef.legacy`); any other view under one of Vario's names is user-owned and never replaced. Anything else is a `SchemaError` and nothing is planned.
- `PlanSchema` (read-only; used for `--dry-run`, with either user) creates the database if missing (`IF NOT EXISTS`), missing tables, `vario_meta`, the destination id, missing views, replacements for Vario's outdated views (`CREATE OR REPLACE`, falling back to `DROP VIEW` + `CREATE VIEW`, else kept with a warning), and finally records the version. Recording the version re-inspects first and refuses if tables or metadata are missing. A schema with a higher recorded version is not touched (`ErrSchemaNewer`). Tables are never altered; no speculative migrations exist.
- `Apply` runs the multi-statement steps against the plan's database, whatever database the admin connection was opened for.
- Runtime (`CheckDestination`): a missing database, missing tables or incompatible objects are errors; delivery stops and data stays spooled until `vario migrate`. A version 1 schema, missing or outdated views and a newer version are warnings. The check runs at startup (with a 5 s timeout, so an offline start is not delayed), again after "unknown table/database" errors, and at the start of a delivery round whenever the last successful check is older than `identityCheckInterval` (1 minute), whether or not rows are queued. A recreated and re-migrated database accepts inserts without any error, so this periodic comparison of the destination id is what detects it under a running collector.
- `doctor --create-schema` is deprecated and runs `vario migrate`; there is one schema-changing implementation.

## Destinations

- The spool (SQLite, `PRAGMA user_version = 1`) has a `destinations` table: normalized endpoint, database, server id (the `destination_id` from `vario_meta`), retirement time. `queue`, `cursors` and `fingerprints` carry `destination_id`; cursors and fingerprints are keyed by it. `Due`, `NextDue`, `Cursor` and `Commit` operate on the selected destination only, so data queued for one destination can never be delivered to another, and a new destination re-reads every source (no inherited cursor or fingerprint).
- **Identity policy**: server id when known, otherwise `config.NormalizeEndpoint(url)` (lower-case scheme and host, explicit default port, no trailing slash) plus database. Credentials are never part of it. `Resolve(endpoint, db, serverID)`: by key; else by server id among other endpoints (alias: the destination is re-keyed and keeps its state); else adopt legacy state; else create. A known server id that differs from the database's is *replaced*: nothing changes until `vario destination switch` retires the old destination and records a new one.
- The collector (`Prepare`, run by `run` and `backfill`) probes the server id, resolves, and activates the configured destination. If the previously active destination still has queued rows, or the database was replaced, it returns a `DestinationError` and does not start (the CLI exits with code 2). Otherwise a change is accepted and logged. This check is in the collector, so direct edits of the configuration file are covered. During operation, a server id that differs from the recorded one stops the collector (identity mismatch, see the periodic check above); the recorded id is not overwritten, so every later start is refused until `vario destination switch` retires the destination and records a new one without cursors, which is then backfilled in full.
- `vario destination switch` first reads the lease. If a live holder exists (not expired, and its process exists when it was taken on this host), it fails at once, changes nothing, and names the holder: command and PID; the background service when the service manager reports that PID; or the other host. It then prints the stop/switch/start sequence. Expired leases and leases of dead local processes are stale and are taken over as before. It never waits for, or stops, a collector. It then holds the lease and keeps, moves (`MovePending`, retry state reset) or discards (`DiscardPending`) the rows of the previous destination, then activates the configured one. Moving or discarding also deletes the previous destination's cursors and fingerprints in the same transaction: they describe those rows as sent to it, so resuming from them after switching back would leave a permanent gap. Without a cursor the destination gets the initial backfill again; `--keep-pending` (and a destination with nothing queued) keeps its state. Moved rows carry their original keys and versions, so the `*_latest` and aggregate views stay correct. Each step (`Replace`, `MovePending` and `DiscardPending` in one transaction each, `Activate` as a single statement) is atomic. An interruption between them leaves either the old state (the collector keeps refusing) or rows already bound to the new destination with nothing queued for the old one (the next start activates the new destination). A unit test covers this, and an integration test covers the whole F1 scenario against real ClickHouse 24.8 and 25.8.
- **Upgrade from spool version 0**: `Open` converts in one transaction. Queue rows get a `destination_id` column; cursors and fingerprints are copied into the new keyed tables; everything is assigned to a *legacy* destination (empty endpoint), which the first `Resolve` adopts for the configured destination. Rows written with `destination_id = 0` (by an old collector after the conversion) are reassigned to it. The conversion is refused while another process holds a live lease. When the configuration changes before the first new-version run, the CLI labels the legacy destination with the previous configuration (`LabelLegacy`), so the old rows are not adopted by the new destination. `OpenReadOnly` reads version 0 files without converting them.

## Configuration of the ClickHouse connection

- `clickhouse.create_database` is still parsed, so existing files remain valid, but it is ignored. It is no longer written to new files, `config show` hides it unless set, and `doctor`, `init` and the collector log warn when it is `true`.
- `CheckConnection` classifies errors by ClickHouse error code (516/192/193/194 authentication, 497 permission, 164/201/452 session restriction, 81 unknown database) and transport error text (TLS vs. network); a missing schema is `migration required`.
